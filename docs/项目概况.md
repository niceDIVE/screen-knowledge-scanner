# screen-knowledge-scanner · 项目概况与技术说明（供外部审核）

> 版本 v3 · 2026-11-03 · 单机个人知识采集整理工具 · MIT
> **仓库地址：https://github.com/niceDIVE/screen-knowledge-scanner**

## 1. 一句话定位

把"人在屏幕上看到的有价值内容"自动沉淀为**可全文检索、可问答的本地知识库**：屏幕截图 → 本地 OCR → 去重拼接 → Markdown 知识库 → Web 控制台检索。全程**默认零网络、零账号自动化、零安装依赖**。

## 2. 项目目标

### 2.1 要解决的问题

- **人工整理太慢**：边浏览边摘抄，内容多时效率极低且难以坚持；
- **传统爬虫不可行**：需要账号凭据、产生异常流量、增加站点负载，且在无 API 的场景根本走不通；
- **素材形态多样**：网页、聊天窗口、文档阅读器——统一到"屏幕"这一个接口，只需要截图和 OCR。

### 2.2 三条设计底线

1. **默认零网络**：采集端只做本机截屏 + 本地 OCR，不产生额外请求；视觉 LLM 为显式开关（默认关），开启后所选截图才会外发到用户自配接口（注意截图含屏幕隐私内容）；
2. **零依赖可部署**：目标机器无需安装运行时/构建链，全部使用 Windows 自带组件（PowerShell 5.1 + .NET Framework + WinRT + GDI+）；
3. **证据链完整**：每份文本保留原始截图；OCR 不可靠处（代码/JSON）进"人工复制清单"，绝不静默出错。

### 2.3 非目标（明确边界）

- 不做全量归档/站点镜像——定位"边读边沉淀"，吞吐随阅读行为；
- 不做无人值守挂机——滚动采集只在人在场时运行；
- 不做云端服务/多用户——单机单用户，127.0.0.1 仅本机访问；
- 不在无授权场景下使用——使用时遵守目标站点条款。

### 2.4 成功标准

| 标准 | 状态 |
|---|---|
| 单键触发采集，人只负责导航 | ✅ 热键 + Web 按钮 |
| 滚动采集可以重叠、不许缺漏 | ✅ 几何保证 + 文本/图像双校验 + 回滚补拍 |
| 全部离线可检索、可留证 | ✅ vault + 截图证据 |
| 重复扫描不产生重复文档 | ✅ 批次幂等哈希 |
| 零安装可部署 | ✅ 纯系统组件 |

## 4. 技术说明

### 4.1 架构与数据流

```
采集层：选区(WinForms) → 热键守护(RegisterHotKey) → GDI+ 截屏(DPI) → 滚动段扫
整合层：Windows.Media.Ocr(WinRT) ⇄ Umi-OCR HTTP 回退 → CJK 归一化 → 锚点拼接 → 幂等
存储层：vault\scans\*.md + vault\_shots\*.png（纯文件态，front-matter 元数据）
服务层：TcpListener 手写 HTTP/1.1 + vanilla JS 控制台（状态/选区/采集/入库/检索/日志）
```

数据单向流动，所有状态落文件，无数据库守护进程，任意环节可人工介入与回滚。

### 4.2 采集层关键实现

- **截屏**：`SetProcessDPIAware` + `CopyFromScreen`，实测 2560×1600@150% 缩放屏必须物理像素采集；选区存 `logs\region.json`，越界自动裁剪。
- **热键**：`RegisterHotKey` 消息循环（`GetMessage` 阻塞，空闲零 CPU；滚动期间 `PeekMessage` 响应中止）——放弃 `GetAsyncKeyState` 轮询（键盘记录器典型行为、易被安全软件误标）。
- **滚动段扫（核心）**：
  - 节奏：步长 2-4 格随机、停顿对数正态（右偏似阅读）、1/10 概率"读帖"停 1.5-3s、1/6 概率回滚一格再看；步数 12 / 总时长 180s 双封顶；
  - 稳定即拍：96px 降采样灰度像素差阈值（<0.5% 视为稳定），4s 超时照拍并标记 `unstable`；
  - **无缺漏保证**：① 几何层（步长 ≤500px ≪ 视口 1600px，相邻帧天然重叠 ≥2/3）＋ 单格位移校准（行剖面互相关，单格过大的应用自动降 1 格/步）；② 文本校验（新帧顶部可用行在上一帧全行中查找，剔除首末行/固定元素/短行；零命中 → 回滚补拍，重试上限 3 次）；③ 图像校验（连续两次滚动后画面变化 <0.5% ⇒ 到底；空帧/纯图/视频帧同样成立）；④ 入库层（补扫帧带 ⚠ 提示）；
  - 环境预检：前台窗口句柄/矩形未变、光标在选区内，变化则暂停等待（60s 超时中止）；步进间光标被移动 → 让出控制权。

### 4.3 OCR 层

- 主后端 `Windows.Media.Ocr`（WinRT）：实测 `StorageFile.GetFileFromPathAsync` 在无包身份进程抛 0x80070005 → 改为 .NET 读字节 → `InMemoryRandomAccessStream` → `BitmapDecoder`；
- 喂图 2x 放大（受 `OcrEngine.MaxImageDimension` 约束自动降档，仅喂 OCR，证据图保持原分辨率）；
- 备用后端 Umi-OCR HTTP 自动回退；任何降级必须显式告警（曾因静默 catch 掩盖回退被评审点名）；
- 后处理：CJK 空格归一化（Windows OCR 会在汉字间插空格，否则全文检索失效）；行序信任引擎原生阅读序（实测 WinRT 投影下 `BoundingRect` 属性在脚本块中静默取 null，主动排序反而打乱）。

### 4.4 整理层

- **锚点对齐去重**：相邻帧重叠 35+ 行是常态，前后缀小窗口匹配必然失配 → 取上一帧末尾"长且唯一"行（归一化 ≥8 字符、帧内唯一）在新帧全行中定位并延长匹配段切割；找不到锚点则保守全保留（宁重复不丢失）。实测：3 帧 30/30/11 行、重叠 15/11 行 → 合并恰好 50 行、首尾对齐、无缺无重；
- **代码/JSON 启发式**：单行 ASCII 引号 ≥3、`"key"：`、行内 `{"` 任一命中即进人工复制清单（OCR 对代码不可靠）；
- **批次幂等**：归一化内容 SHA-256，重复扫描跳过；
- **可选视觉 LLM**：OpenAI 兼容接口做二级结构化，密钥仅环境变量读取。

### 4.5 存储与检索

Markdown vault（Scan 文档含"合并全文（去重后）"+"各帧证据"两段）+ 全文检索（`Select-String`）+ 中文滑窗分词关键词问答。纯文件态，Obsidian 可直接接管。

### 4.6 Web 控制台与安全

- TcpListener 手写 HTTP/1.1 子集（环境实测 HttpListener 不可用）；单线程串行，长操作（入库/LLM）异步化：触发即返回、状态文件轮询；
- 安全：仅绑 127.0.0.1；Host 校验（防 DNS rebinding）；**POST 一律校验 Origin/Sec-Fetch-Site**（Host 校验挡不住 CSRF）；`nosniff`+严格 CSP；头部 8KB 上限、Content-Length 严格校验、拒 chunked；文件访问根目录白化（防穿越）；静态文件白名单；
- 前端：441 行 vanilla JS，textContent 渲染（无 innerHTML），无 CDN/构建链。

### 4.7 工程实证踩坑（供审核参考）

| 坑 | 对策 |
|---|---|
| PS 5.1 将无 BOM UTF-8 按 ANSI 解码，中文注释破坏语法 | 全部脚本强制 UTF-8 BOM，写入管线有 BOM 复检 |
| WinRT `StorageFile.GetFileFromPathAsync` 抛 0x80070005 | 内存流绕开文件代理 |
| WinRT 投影属性在 Sort-Object 脚本块静默失败 | 放弃主动排序 |
| 嵌套 `-match` 覆盖 `$Matches` | 先保存分组再逐行匹配 |
| HttpListener 被环境裁剪 | TcpListener 手写 HTTP 子集 |
| Invoke-RestMethod 双向中文编码错误 | body 发 UTF-8 字节 + RawContentStream 解码 |
| 弯引号字面量被写盘管线规范化成 ASCII 单引号 | 映射表用 `[char]0x` 码位构造 |

### 4.8 已知限制

- OCR 小字号有错字：可检索可留证，引用原文需对照截图或走视觉 LLM；代码块转写不依赖 OCR；
- 吞吐以人类阅读速度为界；Windows 专属；Web 单线程（长操作已异步化）；本地明文存储建议加密盘。

## 5. 前后端构成（审核方关心的分工回答）

**后端为主。** 按代码行数：后端 1,855 行（采集/OCR/整理/HTTP 服务 1,804 + 测试 51），前端 441 行，比例约 **4.2 : 1（后端 ≈81% / 前端 ≈19%）**。

| 职责 | 归属 | 代表技术点 |
|---|---|---|
| 截屏/选区/热键/滚动算法 | 后端 | WinRT、GDI+、RegisterHotKey、像素差、互相关 |
| OCR 与清洗/拼接/幂等 | 后端 | WinRT OCR、锚点对齐、SHA-256 |
| 本地 HTTP 服务与安全 | 后端 | TcpListener、Origin 校验、CSP |
| 状态展示/操作面板/检索界面 | 前端 | fetch、DOM、轮询、textContent |

定性结论：这是**后端/桌面自动化型**项目，前端是薄壳配套层，真正的技术含量在"无 API 约束下用截图+OCR+几何校验保证内容完整"。

## 6. 建议审核关注点

1. 4.2 无缺漏保证的边界：文本校验在密集重复排版（表格）下的锚点失败率；校准互相关的鲁棒性；
2. 4.4 锚点对齐的失败模式：短帧、全重复内容时的保守回退是否可接受；
3. 4.6 Web 安全面：手写 HTTP 子集对畸形请求/慢连接/并发的处理是否充分（当前单线程串行 + 5s 读超时）；
4. 4.8 吞吐边界与 RAG 演进（vault 向量化的取舍）；
5. Windows/PowerShell 生态锁定是否符合长期维护预期。
