# 项目现状与风险报告

> 项目：屏幕知识采集整理工具（截图 → 本地 OCR → 去重入库 → 检索/导出）
> 版本基线：V1（PowerShell）`master`；V2（C#/.NET 10）`0e0a5cf`，CI 绿
> 报告日期：2026-11-04 · 范围：现状核实 + 运行时链路实测 + OCR 引擎选型
> 一句话结论：**功能是通的，但"识别质量"这一环不达标；好在只差两个配置项级的改动 + 一个约 0.5 人日的排序修复，就能把它从"能用但不敢用"推到"可用"。**

---

## 一、结论摘要

1. **能跑通，但不是"可用"状态。** 采集 → OCR → 入库 → 检索 → 导出 的闭合链路实测全绿（本文 §3），但默认引擎的中文识别字符错误率（CER）是 **17.5%**，代码/JSON 场景到 **46%**——这个水平下知识库检索基本失效。
2. **换成 Umi-OCR 后直接达标。** 同测试集同口径：Umi-OCR Rapid 版 **0.3%**、Paddle 版 **3.5%**、系统自带 OCR **17.5%**。差距不是 10%，是 **50 倍**。切换成本是一次配置改动。
3. **有一个必须先修的集成缺陷，否则换引擎也白搭。** 现成 OCR 服务返回的文本块在多栏/表格图上是"列优先"的，直接按返回顺序拼接会把**识别全对的表格（0% 错误）算成 72% 错误**。按坐标重排后同一张图 0%。这是入库文本质量问题，**优先级高于换引擎**。

## 三、本轮量化验证（本文所有数字均可复跑，见附录）

### 3.1 闭合链路（隔离实例，未触碰正式数据）

建批次 → 导入图 2 帧 → 后台 OCR 2/2 成功 → 检索命中 → Markdown → ZIP 导出（34.7KB，含 md + manifest + 原图），全部正常；同图 `sha256` 去重生效；`scroll/stop` 幂等；不存在的批次返回 404、非图片字节返回 400 —— 后端行为正确。

### 3.2 OCR 准确率（CER，越低越好）

| 测试集 | 系统自带 OCR | Umi-Paddle | Umi-Rapid |
|---|---|---|---|
| 核心集（5 张，深浅底 × 10–13pt） | 17.5% | 3.5% | **0.3%** |
| 恶劣矩阵（10 张：细字重 / 9pt / 低对比 / 30 行长文 / 代码 / 路径符号 / 表格 / 渐变底 / 宽屏） | 24.6% | 1.8% | **0.2%** |
| ClearType 变体（更接近真实截屏渲染） | 20.4% | 2.6% | **0.8%** |
| 系统 OCR + 2 倍放大预处理 | 17.5%（几乎无改善） | — | — |

单点最差：**代码/JSON 场景系统 OCR 46.4%**（`{"preset_name":"深度润色"...}` 一行基本读不出来）；正式业务文本里这类行恰恰最需要准确。

### 3.3 资源与部署

| 维度 | 系统自带 OCR | Umi-Rapid | Umi-Paddle |
|---|---|---|---|
| 部署体积 | 0 | 98MB 便携 | 128MB 便携 |
| 额外依赖 | 需系统语言能力包 | 无 | **需 CPU 支持 AVX** |
| 冷启动到首次可用 | 即时 | 3.2s | 4.1s |
| 单次识别峰值内存 | 宿主进程内 | **~0.5GB** | **~1.5GB** |
| 30 行长文耗时 | 0.42–0.86s | 1.5–2.0s | 0.85s |
| 许可 | 系统组件 | MIT / Apache-2.0 | MIT / Apache-2.0 |

选型建议：**主力 Rapid 版**（最准、最省内存、无 AVX 门槛）；Paddle 版仅当"内存充裕 + CPU 支持 AVX + 嫌 Rapid 慢"时用。

## 六、风险与前置条件

1. **全部准确率数据来自合成渲染图**（含 ClearType 变体）。真实客户端截屏还有子像素灰阶与系统缩放差异，真实 CER 可能高于 0.3%–0.8%。**建议方案层面保留"真机终验"这一步，不要拿合成图数字当承诺。**
2. **Rapid 版在长文本上比 Paddle 慢约 2 倍**。若滚动采集节奏压到 700ms/帧，Rapid 可能成为吞吐瓶颈——**这是唯一可能让 Paddle 翻盘的条件**，真机必须复核。
3. **Paddle 版要求 CPU 支持 AVX**，老旧机器会直接启动失败（报 `0xc0000142`）。选 Rapid 可规避。
4. 三个引擎许可均为 MIT / Apache-2.0，商用无阻碍。
5. 当前 OCR 服务是"另一个进程 + HTTP"，需要随软件一起启动/退出管理；不做托管会有孤儿进程与"服务没起来静默降级"两个坑。

## 七、需要决策的三件事

1. **是否批准方案 A（0.7 人日）立即开工**？这是把"功能通"变成"可用"的最小投入。
2. **是否批准方案 C 的两台设备**（双屏机 + 无 .NET 干净机）？不给设备，"多屏 DPI"和"离线部署"这两项永远只能标注"未验证"。
3. **真实截图的采集与使用是否需要审批**（涉及用户屏幕内容与隐私边界）？没有真实样本，准确率数字只能停留在合成图上。

## 附录：数据来源与复跑方式

- 代码仓库 `tests/ocr-bench/`：
  - `make-bench-images.ps1` 生成核心集 5 张（回归判据口径，固定不改）

- 明细文档：`docs/技术选型-OCR引擎-20261104.md`（选型）、`docs/交接文档-复核报告-20261104.md`（逐条核实）、`docs/交接文档.md` §4-T0（回归判据）
- 对比口径：字符错误率 CER = 编辑距离 / 参考字数（去标点与空白后），越低越好；判据线 CER ≤ 5% 可用、≤ 3% 舒适。
