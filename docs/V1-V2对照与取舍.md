# V1 ↔ V2 对照与取舍建议

> 生成：2026-11-03 · 依据：本地实测（构建 + API 冒烟）+ 源码审读
> V1 = `master` 分支（PowerShell 5.1 实现，19 文件）
> V2 = `codex/screen-v2` 分支（C#/.NET 10 重写，57 文件，单提交 `b74a62d`）

## 1. 一句话结论

**V2 是 V1 的工程化重写，方向正确、质量明显更高**；V1 的价值退化为"零依赖可跑的最小实现 + 算法原型"。建议 **V2 作为主线**，V1 冻结归档（保留其零安装优势与踩坑记录）。

## 2. 规模与形态

| 维度 | V1（master） | V2（codex/screen-v2） |
|---|---|---|
| 语言 | PowerShell 5.1 + .NET Framework | C# / .NET 10 + ASP.NET Core + SQLite FTS5 |
| 文件数 | 19 | 57 |
| 后端代码 | 1,804 行（bin）+ 51（tests） | **1,050 行**（src）+ 235（tests） |
| 前端代码 | 441 行 | **1,851 行**（app.js 534 / index.html 221 / style.css 1,096） |
| 前后端比例 | 后端 : 前端 ≈ 4.2 : 1 | **前端 : 后端 ≈ 1.7 : 1**（前端更重） |
| 部署 | 零安装，系统组件直跑 | 需 .NET 10 SDK 或发布自包含包 |
| 跨平台 | Windows 专属 | 通用构建可在 Linux 跑图片导入流程 |
| 构建产物 | 无 | `scripts\publish-windows.ps1` 出 win-x64 self-contained zip |
| CI | 无 | GitHub Actions（ubuntu test + windows publish 双 job） |

> 有意思的翻转：V1 是后端为主（80%），V2 变成**前端为主**（CSS 1,096 行说明 UI 工程化了）。如果这是"求职作品"用途，V2 反而更像全栈项目。

## 3. 架构与数据模型

| 维度 | V1 | V2 |
|---|---|---|
| 存储 | Markdown 文件 + PNG，front-matter 元数据 | SQLite（`runs`/`frames`/`jobs`/`ocr_results`/`run_notes`/`settings`/FTS5 `search`）+ 原图 SHA-256 内容寻址（`images/`） |
| 事务 | 无（文件系统即状态） | 序号分配与帧记录同事务；原图先临时文件再原子移动 |
| OCR 执行 | 同步（截屏 → OCR 一次完成） | **任务队列**：`jobs` 表 pending/processing/succeeded/failed，进程重启自动恢复中断任务，失败保留错误可重试 |
| 历史 | 覆盖（重跑覆盖 md） | `ocr_results` 不可覆盖的识别+校对历史，`revisions` 可查 |
| 幂等 | 归一化内容 SHA-256 跳过重复批次 | 同原图+同文字可折叠，帧记录独立保留 |
| 导出 | Markdown + 截图引用 | ZIP（scan.md + manifest.json 含修订历史 + images/） |

**判断**：V2 的数据模型是这轮升级的最大价值——V1 的"文件即状态"在多批次/重试/校对场景下会失控，V2 的关系模型把"证据不可变 + 结果可重跑"这条原则落到了 schema 上。

## 4. 采集与算法

| 维度 | V1 | V2 |
|---|---|---|
| 截屏 | GDI+ + DPI 感知，虚拟屏 | GDI+ + `EnableDpiAwareness`，区域可配 |
| 热键 | RegisterHotKey 消息循环 | `HotkeyService`（WinForms 消息循环）——同一方案，工程化包装 |
| 滚动控制 | 节奏随机（步长 2-4 格/对数正态停顿/回读）+ 总时长上限 | `ScrollCoordinator` 状态机（idle/waiting/running/needs-review/completed/stopped/failed）+ 3 分钟 CancellationToken + 参数校验（1-30 步/300-5000ms/1-3 格） |
| 位移估计 | 行剖面互相关 → 单格位移校准 | `MotionEstimator`：缩略灰度图全位移搜索 + **置信度 + 备选唯一性**判定，不可靠即停 |
| 稳定判定 | 像素差 <0.5%，4s 超时照拍 | 连续 5 次采样差异 <0.004，超时写 note 并保留 |
| 缺漏处理 | 文本校验（可用行）+ 图像级不动 + 回滚补拍（上限 3 次） | **重叠 <0.4 或不可靠 → 直接停止自动滚动并留证**（needs-review） |
| 去重拼接 | 锚点对齐（长且唯一行 ≥8 字符） | 保守连续重叠（≥3 行且 ≥40 字符才删），否则保留全文并提示 |
| 首帧 | 无强制 | **滚动前先存首帧**（测试 `InitialEvidenceIsSavedBeforeAnyScroll` 专测） |

**判断**：V2 在"安全失败"上的取向更明确——V1 会尝试自动回滚补拍（可能陷入重试），V2 选择**停下等人**。对证据类工具，V2 的取向更对；V1 的回滚补拍可以作为可选能力后续再引入。

## 6. 风险与信任边界

- V2 是**另一个 Agent（Codex）的产物**，我做的只是构建与冒烟，**未逐行审读全部 1,050 行**；
- V2 README 自己承认："交叉构建通过不等于热键、WinRT、屏幕或 DPI 行为已经在 Windows 实机验收"；
- V2 依赖 .NET 10 SDK（本机已装 10.0.203）与 NuGet 联网 restore（实测有 SSL 重试但成功）；
- 两版都**没有**做过隐私/安全审计。**已确认 V2 的 Web 安全层缺失**：`Program.cs`（144 行）只有异常处理中间件，**没有** V1 具备的 Host 校验、Origin/CSRF 校验、CSP、`nosniff`、路径白化——V2 使用 ASP.NET Core 默认静态文件与最小 API，静态文件路由本身较安全，但跨站 POST 触发采集/滚动仍可能被任意网页发起。这是 V2 相对 V1 的**明确倒退**，上线前必须补。

## 7. 取舍建议

| 用途 | 建议 |
|---|---|
| 日常使用 | 用 V2（数据模型稳、可重试、可导出 Obsidian） |
| 零安装应急/无 .NET 环境 | 保留 V1（系统组件直跑） |
| 求职/作品展示 | V2（全栈 + CI + 测试 + 发布包） |
| 算法参考 | V1 的锚点对齐与回滚补拍、V2 的 MotionEstimator 置信度判定，各自取长补短 |

**两条线并行维护的成本**不建议；建议 V2 主线 + V1 打 tag 归档。
