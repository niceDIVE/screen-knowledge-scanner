## 2. 本轮三条结论

1. **阅读顺序的根因不是"我们丢了 box"，而是"排版解析方案选错"。** 实测：同一批图，Umi 的 `tbpu.parser` 取 `single_*` 时表格 CER **0%**、取 `multi_*` 时 **80.6%**；双栏正文反过来（`multi_*` 0.8%，`single_*` 77.3%）。**所以"无条件坐标重排"是错的**——我的原型对表格有效，却把双栏拆成 77.3%。
2. **适配层改两件事就够**：①把 parser 作为配置项传下去（默认 `single_para`，双栏切 `multi_para`）；②不再按 `'\n'` 硬拼，改用 Umi 的 `end` 字段 + 矩形 y 中心补换行（表格的 `end` 常是空格，只靠它会挤成一行）。
3. **Rapid 已接入完整链路并通过验收**：入库、检索、导出全通，`/api/status` 版本号改为从构建元数据读取（实测 `2.2.0`）。

## 4. 版式实验（决定实现方案的那组数据）

测试集 `tests/ocr-bench/layout/`（4 张，新增）：表格 5×4、双栏正文各 7 行、代码 5 行、JSON 6 行。

| 版式 | `multi_*` | `single_*` | 通用坐标重排（我的原型） | `data.format=text` |
|---|---|---|---|---|
| 表格 | 80.6% | **0%** | 80.6%（判错） | 80.6% |
| 双栏正文 | **0.8%** | 77.3% | 0.8%（判对，靠误判） | 0.8% |
| 代码 | 1.7% | 1.7% | 100%（判错） | 1.7% |
| JSON | 0% | 0% | 100%（判错） | 0% |

> 原型按「x 投影找空白带 → 判列数 → 窄格判表格」做的自动判别，在代码/JSON 上把行间空隙误判成列，输出被拆坏（100%）。**结论：不做通用自动重排，改为「parser 可选 + 几何补换行」**，双栏由配置显式切换，后续若要自动识别，需要单独做带标注集的判别器。

另外 10 张恶劣矩阵（细字重/9pt/低对比/长文/宽屏等）上，各 parser 结果完全一致（均 0–0.5%），**说明默认 `single_para` 不会在单栏正文上产生回归**。

## 6. 上一轮两条结论的更正（复核后）

| 上一轮说法 | 复核结果 | 更正后表述 |
|---|---|---|
| 「单字 `念` 0 命中」作为 bigram 检索缺陷的证据 | **归因错误。** `KnowledgeStore.cs:282-287` 有专门分支：`query.Trim().Length == 1` 时走 `instr(lower(ocr_text), $query)` 子串匹配，不查 FTS。我那次查询的字根本不在测试图里 | 单字查询**有**实现；`世界 书` 这类「拆开的双字 + 单字」仍会 0 命中（bigram 设计取舍），单字本身不是缺陷 |
| 「前端完全不显示 aborted / needs-review」 | **过重。** `app.js:485-487` 确实把 `status.scroll.note` 渲染到 `capture-hint`（`style.css:490` 有独立样式块）。真实问题是：①只有一句纯文本，**没有状态语义与配色**，`aborted`/`needs-review`/`completed` 视觉上无区别；②`completed` 两处（`ScrollCoordinator.cs:122/125`）不传 note → 正常结束时**什么都不显示**；③提示仅在 `scroll.runId` 等于当前批次时显示 | T11 应表述为「已有 note 文本通道，缺状态徽标/配色/结束提示」，不是「完全无提示」。仍是 P1，但工作量从"从零实现"降到"加状态语义与样式" |
