## 2. 现在能做什么（操作手册）

### 启动 / 停止

```powershell
# V1（PowerShell，零依赖）
powershell -File bin\start-web.ps1          # 启动并开浏览器（8788）
powershell -File bin\start-web.ps1 -Stop     # 停止

# V2（C#/.NET）
powershell -File screen-v2\scripts\run-windows.ps1 -Port 8800 -NoBrowser   # 前台
# 或双击桌面「屏幕扫描机器人 V2」（隐藏控制台，自动开浏览器）

# 停止 V2：关闭其控制台窗口，或 taskkill 该 dotnet 进程
```

### 日常流程（V2 为例）

1. 页面点「框选区域」→ 拖出阅读区（热键 `Ctrl+Alt+R` 也可，被占用时见 §6-3）
2. 在目标窗口里把鼠标放进选区 → 点「滚动采集」（`Ctrl+Alt+W`）
3. 停止用 `Ctrl+Alt+Q`（`aborted` = 目标失活，`needs-review` = 重叠无法确认，都不是故障）
4. 点「处理 inbox」→ 后台 OCR → 回车
5. 搜索框查关键词；「导出」拿 ZIP（Markdown + manifest + 原图）

### 端口与冲突

- V1 端口在 `config.psd1` 的 `Web.Port`（**8788**，被占时自动 +1 试 10 个）
- V2 端口在 `screen-v2\scripts\run-windows.ps1` 的 `-Port`（默认 **8800**）与 `appsettings.json` 的 `Urls`
- **历史坑**：8787 被桌面程序 `cmdc-pak(2).exe` 占用，V1 会顺延到 8788；V2 原默认也是 8788 → 冲突导致 V2 静默退出。现已将 V2 移到 8800
- V1 顺延逻辑实测：`web-server.ps1:406` `foreach ($tryPort in $Port..($Port + 10))`，起点 8788 → 最多试到 **8798**（不含 8800，所以两者不会抢端口）

### OCR 引擎（中文准确率的关键开关）

- `appsettings.json` 的 `Scanner:OcrEngine`：`auto`/`windows` → 系统 OCR；`umi` → Umi-OCR（HTTP 1224）；其它值 → Tesseract
- **选型结论（2026-11-04，详见 `docs\技术选型-OCR引擎-20261104.md`）：主力用 Umi-OCR，优先 Rapid 版**；Paddle 版备选；Windows 本地 OCR 只做兜底
- 三档实测（同测试集、同口径 CER）：Windows 本地 OCR **17.5%** / Umi-Paddle **3.5%** / Umi-Rapid **0.3%**；恶劣矩阵（细字重、9pt、代码、表格）Windows 24.6% vs Rapid 0.2%
- 资源差别很大：Rapid 单次识别峰值工作集 **~0.5GB**、无 AVX 要求；Paddle 峰值 **~1.5GB**、需 AVX；Windows 零部署但精度不可用（放大 2 倍预处理也只从 20.4% 降到 17.5%）
- 切到 umi 的步骤：启动 Umi-OCR（HTTP 服务默认 `127.0.0.1:1224`）→ 把 `Scanner:OcrEngine` 改成 `"umi"` → 重启 V2；`/api/status` 的 `ocrEngine` 应显示 `Umi-OCR`
- **前置改造**：Umi 返回的文本块在多栏/表格图上是列优先的，必须按 box 坐标聚行重排，否则表格 CER 会从 0% 虚高到 72%

## 6. 已知问题与陷阱（务必先读）

1. **PS 5.1 的 BOM 陷阱（最高频事故）**：任何 `.ps1/.psd1` 无 UTF-8 BOM 时，PS 5.1 按 GBK 读中文注释 → 语法/解析错误。**用编辑器或脚本改过这些文件后，必须补 BOM**：
   ```powershell
   Get-ChildItem -Recurse -Include *.ps1,*.psd1 | ForEach-Object {
     $c=[IO.File]::ReadAllText($_.FullName,(New-Object Text.UTF8Encoding $false))
     [IO.File]::WriteAllText($_.FullName,$c,(New-Object Text.UTF8Encoding $true)) }
   ```
   本轮就因 `config.psd1` 丢 BOM 导致 V1 完全起不来。
2. **本机 `dotnet test` 跑不了**：testhost 在 `SetParentProcessExitCallback` 抛 `Win32Exception(5)`（进程句柄权限），与代码无关。**测试只能靠 CI 或普通桌面会话**。已写入 V2 README。
3. **热键被占用**：本机 `Ctrl+Alt+R` 被其他程序占用。改 `appsettings.json` 的 `Scanner:HotkeyKeys:Region`，或从页面按钮框选。
4. **周期内容整周期滚动不可判定**：重复排版滚满一个周期后两帧完全相同 → 判"未移动"。这是已知边界，`MotionEstimatorTests` 固化了该行为，不要试图"修掉"它。
5. **V2 快捷方式依赖 `screen-v2` 目录存在**：目录被删/改名会弹 MsgBox 提示重新克隆。
6. **V2 首次启动会 build**（约 20 秒），双击后浏览器稍晚打开属正常。
7. **默认 OCR 引擎选错，代价是 5 倍误差**：`OcrEngine: auto` 在 Windows 上解析到系统 OCR，中文正文 CER **17.5%**（代码/JSON 46%），JSON 行基本读不出来。**已选型：主力用 Umi-OCR Rapid 版（CER 0.3%，峰值内存 ~0.5GB），Paddle 版备选（3.5%，峰值 ~1.5GB，需 AVX）**，见 `docs\技术选型-OCR引擎-20261104.md`。Windows OCR 只做兜底，且必须在 UI 上提示「识别质量较低」。
7.1 **Umi 的结果必须先按坐标重排再入库**：Paddle/Rapid 返回的文本块在多栏/表格图上是**列优先**的，直接按返回顺序拼接会把识别全对（0%）算成 72%。按 box 聚行重排后 Paddle 9.0%→1.8%、Rapid 7.5%→0.2%。这是集成侧缺陷，不是引擎问题。
7.2 **杀 Umi 要连子进程一起收**：只杀 `Umi-OCR.exe` 会留下 `PaddleOCR-json.exe` 孤儿（实测 1.8GB 常驻）。
8. **导出不做跨帧去重**：同一张图重复采集时 `images\` 只存一份（按 sha256 去重，已验证），但 `/api/runs/{id}/export` 会按帧在 ZIP 里各打一份 `images/<frameId>.png`，导出体积随帧数线性膨胀。
9. **畸形 multipart 返回 500**：坏 boundary / 非法 body 在 `ReadFormAsync` 抛 `InvalidDataException`，不在 `Program.cs:81` 的异常白名单里 → 500 而非 400。正常路径是对的（不存在的 run → 404、非图片字节 → 400）。
10. **检索是中文 bigram 索引**（`KnowledgeStore.cs:61` fts5、`:270` 分词、`:282` 单字回落）：`世界`/`世界书`/`星野`/`JSON` 能命中，但 `世界 书`（拆开的双字 + 单字）0 命中，单字 `念` 也 0 命中。这是设计取舍，不是故障，别去「修」。
11. **`screen-v2\` 里还带一份 V1 副本**（`screen-v2\bin\` 9 个脚本 + `screen-v2\config.psd1`），端口已漂：根目录 **8788**、副本 **8787**。改 V1 时先确认改的是根目录那份。
