## 2. P0（阻塞发布）

### F-01 Web 层缺少安全防护，V1 有而 V2 没有

- **现象**：`Program.cs:32-45` 只有异常处理中间件；全文件无 Host 校验、无 Origin / Sec-Fetch-Site 校验、无 CSP、无 `X-Content-Type-Options`、无路径白化。
- **对比 V1**：`bin/web-server.ps1` 具备 Host 头校验（防 DNS rebinding）、POST 一律校验 Origin/Sec-Fetch-Site（防跨站 CSRF）、`nosniff` + 严格 CSP、`Resolve-InRoot` 根目录白化。
- **实际攻击面（已核对哪些端点可被跨站触发）**：
  - 无 body 的 POST 属 simple request，不触发预检、浏览器不拦：`/api/region/pick`（`Program.cs:96`，会弹出全屏选区覆盖层——骚扰）、`/api/scroll/stop`（`Program.cs:108`，可中止采集）、`/api/frames/{id}/retry`（`:83`，需已知 frameId）；
  - `multipart/form-data` 上传（`/api/runs/{id}/frames`，`:69`）同属 simple request，知道 runId 可被跨站写入图片；
  - 带 JSON body 的端点（capture / scroll/start / runs / region）会因无 CORS 响应头在预检阶段被浏览器挡下——**这是浏览器默认行为，不是服务端防护**，换成非浏览器客户端即可绕过。
- **影响**：用户浏览任意恶意页面时，该页面可静默触发上述动作；本地知识库可被外部页面间接操控（数据不出本机，但行为被劫持）。
- **建议**：加一个最小中间件统一处理
  1. 仅接受 `Host` 为 `127.0.0.1:<port>` / `localhost:<port>`；
  2. POST/PUT/PATCH/DELETE 校验 `Origin`（缺省放行本机非浏览器客户端）与 `Sec-Fetch-Site: same-origin|none`；
  3. 全部响应加 `X-Content-Type-Options: nosniff` + 严格 CSP（`default-src 'self'`）；
  4. 静态文件与 `/api/images/{id}` 的路径拼接再校验一次位于数据目录内（当前 `ImagePath(sha256)` 由数据库取 SHA 拼接，风险低但建议固化为白化函数）。
- **待回执**：是否接受？若接受，计划版本与实现方式（中间件 / 端点过滤器）？

## 3. P1（影响可用性与部署安全）

### F-02 发布包数据目录落在程序目录内，升级容易丢数据

- **现象**：`Program.cs:9` 用 `Path.GetFullPath(options.DataDirectory, AppContext.BaseDirectory)`；`appsettings.json` 的 `DataDirectory` 默认 `"data"`；`scripts/publish-windows.ps1` 未覆盖该配置 → 发布版数据在 `artifacts/<rid>/data/`。
- **影响**：用户按 README 解压新版到新目录（或先删旧目录）时，旧 `data/`（SQLite + 原图）随目录一起消失；`scripts/run.sh` 显式传了 `--Scanner:DataDirectory="$project_root/data"`（开发态安全），发布脚本没有对应处理。
- **建议**：发布默认改到 `%LOCALAPPDATA%\Screen\data`（或首次启动引导用户选目录），并在 `发布说明` 明确"升级请保留 data 目录"。
- **待回执**：选择哪种默认？是否接受迁移逻辑（旧目录存在则复用）？

### F-03 单帧截屏路径缺少前台窗口/光标校验

- **现象**：`Program.cs:101-106` 的 `/api/capture` 只有 `await Task.Delay(3000)`，随后直接 `scroll.Single(...)`；而滚动路径在 `ScrollCoordinator.cs:59,83` 有 `capture.IsTargetActive()` 校验（窗口或光标变化即停）。
- **影响**：用户点页面按钮后在 3 秒内切到了别的窗口，会截到无关窗口（含隐私内容进库）；两条路径行为不一致。
- **建议**：单帧路径复用 `BeginSession` + `IsTargetActive`，或在 `Capture()` 前校验前台窗口句柄/光标是否在选区内。
- **待回执**：是否补齐？

### F-04 Windows 专属代码零自动化测试覆盖

- **现象**：`ci.yml` 的 `windows` job 只做 publish（`:21-27`），不跑 test；`ubuntu` job 跑 test，但 `Screen.App.csproj:18-20` 用 `Compile Remove="Windows/**/*.cs"` 把 Windows 实现排除在外。
- **影响**：`WindowsCapture` / `WindowsOcr` / `HotkeyService` / `RegionPicker` 以及 DPI、WinRT 解码路径完全靠人工验证；README 也自认"交叉构建通过不等于实机验收"。
- **建议**：windows job 增加 `dotnet test`（Windows 目标构建下跑），或至少对这些类做可注入的抽象测试（如 `Gray` 缩放、区域裁剪数学）。
- **待回执**：是否在 CI 增加 Windows 测试任务？

### F-05 单元测试在受限运行环境无法执行（环境问题，需要你确认是否为已知限制）

- **现象**：本机 `dotnet test` / `dotnet vstest` 均失败：testhost 在 `DefaultEngineInvoker.SetParentProcessExitCallback` → `Process.GetProcessHandle` 处抛 `Win32Exception(5) 拒绝访问`；用独立进程隔离启动同样失败。
- **判断**：这是本机进程句柄权限限制，不是代码缺陷；但意味着"本机无法自证测试通过"，只能依赖 CI。
- **建议**：文档补一句"若 `dotnet test` 报 testhost Win32Exception(5) 属宿主环境限制，请到 CI 或普通会话运行"。
- **待回执**：你侧 CI 上 `dotnet test` 是否全绿？给出最近一次运行的用例数/通过数。

## 4. P2（体验与一致性）

### F-06 `/api/capture` 的 3 秒等待硬编码

- **证据**：`Program.cs:104` `await Task.Delay(3000, token)`。
- **建议**：放进 `ScannerOptions`（如 `CaptureFocusDelayMs`），前端倒计时展示。

### F-07 稳定判定窗口偏短（1 秒）

- **证据**：`ScrollCoordinator.cs:56-64`：5 次采样 × 200ms；超过即写 note "部分画面在等待期间仍有变化"。
- **影响**：图片懒加载/GIF/视频播放在采集区时，几乎必然触发该 note，用户看到大量"需要核对"。
- **建议**：窗口可配置（默认拉长到 2–3s），或按"变化区域占比"而非"有无变化"判定。

### F-08 缺少视觉 LLM 二级结构化（相对 V1 的功能缺项）

- **现象**：V1 有可选开关（`config.psd1` VisionLLM：OpenAI 兼容接口，对疑似代码/复杂截图做二次转写）；V2 只把代码/JSON 标记进"需要核对"，无二次转写能力。
- **建议**：评估是否保留该能力（可用也可明确声明"不做"，请在文档中给出取舍理由）。
- **待回执**：计划纳入还是明确不做？

### F-09 幂等语义变化需要文档说明

- **现象**：V1 对完全相同的批次内容做哈希跳过；V2 是"同图共享文件 + 每次观察独立保留帧记录"，不跳过批次。
- **判断**：V2 语义更符合"证据链"原则，但迁移用户可能预期"重复扫描不产生重复记录"。
- **建议**：在 README/使用说明里明确两代语义差异与推荐工作流（何时新建 run）。
