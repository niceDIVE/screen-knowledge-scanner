## 2. 新发现（文档未记，建议升为正式测试项）

### F-01【P0】中文正文 OCR 准确率不达标，检索直接失效

用仓库自带 `tests\make-test-image.ps1` 生成的中文截图（Microsoft YaHei 10pt，900×560）走真实链路，Windows OCR(zh-Hans-CN) 输出与原文比对：

| 原文 | 识别结果 |
|---|---|
| 预设的**排版**要**控制** token 密度，**别把正文挤掉了** | 预设的**扳**要**崆制** token ， **别吧正艾懵原了** |
| 收到，我把世界书的插入**点整体**后移了**一格**，**生成稳定**多了 | 收到，我把世界书的插入**整恤**后移了**一袼**，**生成定**多了 |
| 上面这种 JSON 记得手动**复制**，OCR 会**认错引号和花括号** | 上面泫种 JSON 记得手动**思制**，0R 会**认宿引号和花后号** |
| 楼主整理的世界书**分批触发**写得很好，**链接我收藏了** | 仁主整还的世界书**分扌比齷**写得很好，**旨寿我收藏了** |

字符错误率（去标点/空白后 Levenshtein）：行1 **40.9%**、行2 **16.7%**、行3 **23.1%**、行4 **31.8%**，**合计 CER = 27.7%（94 字错 26 字）**。

后果实测：`/api/search?q=排版` → **0 命中**；`q=深度润色` → **0 命中**；`q=世界书` → 2 命中（碰巧识别对）。也就是说**知识库能不能被检索到，取决于 OCR 恰好认对没认对**。

### F-02【P0】前端不展示采集终止原因（对应文档 T11，实为缺陷不是「已支持」）

后端写入 `aborted` / `needs-review`（`ScrollCoordinator.cs:106/117/131`），前端 `app.js` 无任何对应文案/颜色分支。用户看到的只有 `capture-hint` 里的一句 note 文本（`app.js:487`，容器样式 `style.css:490` 与状态无关）。文档 T11 的前提描述需要改写成「待实现」。

### F-03【P2】同图去重：库内去重、导出不去重

同一张图连续上传两次：`sha256` 相同、`images\` 目录只有 1 份原图（去重生效 ✅）；但 `/api/runs/{id}/export` 的 ZIP 里按帧各打一份（`images/<frameId>.png` ×2，各 19,517 B）。导出体积随帧数线性膨胀。

### F-04【P2】畸形 multipart 返回 500 而非 400

- 合法 multipart + 不存在的 run → **404** ✅
- 非图片字节 → **400** ✅
- 坏 boundary/畸形 body → **500**（`ReadFormAsync` 抛 `InvalidDataException`，不在 `Program.cs:81` 的异常白名单内）

### F-05【P3】检索是中文 bigram 索引，有已知行为边界

`KnowledgeStore.cs:61` `fts5(frame_id UNINDEXED, tokens)`、`:270` `Words()` 分词、`:282` 单字回落到源文本。实测：`世界`/`世界书`/`星野`/`JSON`/`preset`/`temperature` 均 2 命中；`星野 世界书`（双词）2 命中；`世界 书`（拆开的双字+单字）**0 命中**；单字 `念` 0 命中。这是设计取舍，但应写进文档，否则用户会当成 bug。
