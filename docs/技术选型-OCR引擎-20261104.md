# 技术选型：本地中文 OCR 引擎（2026-11-04）

> 决策范围：屏幕截图 → 本地 OCR → 知识库检索，这条链路里「选哪个 OCR 引擎」
> 依据：① 本机自测（18 组数据，见 §2–§4）② 社区一手资料（见 §5）
> 复跑：`tests\ocr-bench\`（出图脚本 + 三套打分脚本，全部可重跑）
> 相关：`docs\交接文档.md` §4-T0、`tests\ocr-bench\result-20261104-ab.md`

---

## 1. 结论（先给答案）

1. **主力引擎：Umi-OCR，优先 Rapid 版**（内置 RapidOCR/ONNX）。理由是**同一批图上它最准、最省内存、无 AVX 依赖**：核心集 CER 0.3%，恶劣矩阵 0.2%–0.8%，空闲内存 388MB。
2. **Paddle 版作为备选**：同条件下 CER 1.8%–3.5%，内存**峰值约 1.5GB（Rapid 的 3 倍）**，长文本快约 2 倍，但要求 CPU 支持 AVX。只有在「机器内存充裕且 CPU 支持 AVX、且嫌 Rapid 慢」时才选它。
3. **Windows 本地 OCR 不做主力**：核心集 17.5%、恶劣矩阵 20.4%，代码/JSON 场景 46%，**放大 2 倍预处理也只从 20.4% 降到 17.5%**（救不回来）。它只保留为「没装 Umi 时的兜底」，且 UI 必须显式提示「识别质量较低」。
4. **比换引擎更划算的一件事：坐标重排**。Paddle/Rapid 返回的文本块在多栏/表格图上是**列优先**的，按返回顺序拼接会把 0%（识别全对）算成 72%（顺序全乱）。改成按 box 坐标聚行重排，Paddle 从 9.0% → 1.8%，Rapid 从 7.5% → 0.2%。**这是集成侧缺陷，不是引擎精度问题，必须先修**，否则换哪个引擎都白搭。

ClearType 次像素抗锯齿（更接近真实截屏，`matrix-ct\`）：Windows **20.4%** / Paddle sorted **2.6%** / Rapid sorted **0.8%** —— 排序不变。

Windows OCR 的放大预处理实验（`matrix-ct2x\`，2× HighQualityBicubic）：**17.5%**，仅比 20.4% 略好，且长文本反而从 11.3% 劣化到 25.4%（放大改变了行切分）。**结论：预处理不是 Windows OCR 的救命稻草。**

## 4. 资源、速度、部署、许可

| 维度 | Windows 本地 OCR | Umi-Rapid | Umi-Paddle |
|---|---|---|---|
| 部署体积 | 0（系统自带） | 98MB 便携版 | 128MB 便携版 |
| 额外依赖 | 需装 `Language.OCR.zh-Hans` 能力包 | 无 | **需 CPU 支持 AVX**（否则 0xc0000142 / OCR init fail） |
| 冷启动到首次可用 | 即时 | **3.2s** | **4.1s** |
| 常驻内存（同一 30 行长文一次识别的峰值工作集 / 空闲私有内存） | 宿主进程内 | **0.48GB / 0.59GB** | **1.5GB / 0.85GB** |
| 单图耗时（30 行长文） | 0.42–0.86s | 1.5–2.0s | **0.85s** |
| 单图耗时（短图） | 0.41s | 0.16–0.4s | 0.10–0.4s |
| 接口形态 | 进程内 WinRT | HTTP `127.0.0.1:1224/api/ocr` | 同左 |
| 许可 | 系统组件 | MIT（Umi）/ Apache-2.0（RapidOCR） | MIT（Umi）/ Apache-2.0（PaddleOCR） |

> 耗时统计口径：V2 走队列轮询有 400ms 粒度，另用直打 HTTP 测了一轮（**Rapid 0.12–0.22s，Paddle 0.09–0.24s**，短图两者相当）。
> 运维坑（实测）：直接杀 `Umi-OCR.exe` 会留下 **1.8GB 的 `PaddleOCR-json.exe` 孤儿进程**，必须连子进程一起收。

| [docling 四引擎横评](https://github.com/yihong0618/bilingual_book_maker/blob/a160326ef9ca5d39db6f364ed3546babf2c59eea/docs/zh/evaluation/pdf-ocr-engines.md) | 中文 CER：rapidocr 0.055 / ocrmac 0.088 / tesseract 0.155 / easyocr 0.632（印刷扫描件） | 方向一致：**Rapid 系 > Tesseract 系**；Rapid 优于 Paddle 也与我们一致 |

| 厂商 FAQ + 微软文档 | 小字要求文字高度 ≥ 约 20px 才稳 | 我们的 9pt（≈12px）用例 Windows 30.5% / Rapid 0%，**同向印证** |
| 广州软件院 12 款横评 | 印刷中文前三含 RapidOCR，PaddleOCR 未进前三（分数在图内未取到） | 仅作旁证，未采信数值 |

**社区没有的、我们补上的**：Windows 本地 OCR 与 Paddle/Rapid **同测试集同口径的 CER 对比**（公开资料里查不到一手数字）。上表 §2–§3 就是这份缺口的数据。

## 6. 落地改造清单（按性价比排序）

| # | 改动 | 收益 | 工作量 |
|---|---|---|---|
| 1 | **Umi 结果按 box 坐标聚行重排**（V2 `Ocr.cs` 的 `UmiOcr`；V1 `capture-ocr.ps1:135`） | CER 9% → 1.8%（Paddle）/ 7.5% → 0.2%（Rapid），表格与多栏直接可用 | 半天，含单测 |
| 2 | **引擎配置成 `umi`**（`appsettings.json` / `config.psd1`），并在启动时探活 `UmiUrl` | CER 17.5% → 0.3%，一次性 | 10 分钟 |
| 3 | **兜底可见**：Umi 不可用回退 Windows OCR 时，`/api/status` 带 warning，前端顶栏标「识别质量较低，建议安装 Umi-OCR」 | 避免用户以为「识别就是这水平」而弃用 | 2 小时 |
| 4 | Umi 生命周期托管：启动前探活 1224，退出时连子进程一起收（避免 1.8GB 孤儿） | 稳定性 | 2 小时 |

> 不建议做：给 Windows OCR 加放大预处理（实测只从 20.4% 到 17.5%，收益不足以抵消复杂度）。

## 7. 风险与未验证

- **未用真实客户端截屏验证**：全部测试图是 GDI+ 渲染合成（含 ClearType 变体）。真实 Discord/浏览器截图还有子像素灰阶、ClearType 调谐、系统缩放差异，真实 CER 可能比 0.3%–0.8% 略高。**建议补 10 张真实截图**再定稿阈值。
- **未测 CJK 之外的多语言**（日韩/繁体），产品当前只面向简体中文。
- **未测超长图**（>4096px 高，Windows OCR 有 MaxImageDimension 限制；Umi 侧未测分块行为）。
- **Rapid 在长文本上比 Paddle 慢约 2 倍**（1.5–2.0s vs 0.85s）。若滚动采集节奏压到 700ms/帧，Rapid 会成为瓶颈——**这是唯一可能让 Paddle 翻盘的条件**，真机上要复核吞吐。
- 社区关于「Paddle 更准」的说法与我们数据相反，**已按自测数据决策**；若后续在真实截图上出现反转，改回 Paddle 只需换端口与配置，成本极低。
